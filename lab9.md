## The Digital Sequence Recognition Lock

Black-n-Gold Digital System Solutions has tasked you with creating a new kind of lock for their lockboxes.  This particular lock will accept a sequence of 1s and 0s, and will unlock if the correct sequence is entered.  The lock will only use buttons 0 and 1, as well as W to set the initial password or to relock the lock once opened, and a button to reset the entire system (we'll use `reset`, which is set to logic high when 3-0-W are asserted together).

Video demonstration of the lock can be downloaded from [here (src/lab9lock.webm)](src/lab9lock.webm) 

The lock must use a sequence recognizer (or detector) to determine if the correct sequence of buttons is being pressed.  If even one mistake is made, the lock should trigger its alarm.

> **⚠️ Attention:**
>
> Sequence recognition is crucial to data transmission between hardware components. When a computer begins a transmission of data to another computer, a sequence recognizer on the receiving end can be used to determine what data was received, and whether it was received correctly.  It's crucial to a lot of digital communication protocols - including the one used to transfer all this data from Purdue servers to the computer you're sitting at.
>
> It's a little difficult to emulate two computers communicating with each other in a lab, so we'll use the sequence recognizer for a different purpose - determining if the correct sequence of buttons was pressed to unlock this lock. Data itself is transferred in binary - 0s and 1s, so we can simply store these bits in a linear shift register, much like we'll do here.  In this scenario, we're storing the received data in a shift register, and then receiving a second sequence which we're comparing against the first, unlocking the lock if it matches or triggering an alarm if it doesn't.

Two of the modules come from your lab assignment - `clock_psc` and `keysync`.  The `clock_psc` module is a _clock prescaler_, which will be used to flash the red LED at a rate of 2 Hz when the lock is in the ALARM state.  (You'll use a version of this in ECE 36200.) In the lab itself, you will implement the remaining modules:

- `sequence_sr` - a shift register to hold the sequence of 1s and 0s.  This will store the sequence of buttons pressed by the user.
- `fsm` - a state machine to control the lock.  This will determine if the lock is waiting for a user to enter the initial sequence or to re-enter the sequence to unlock it, if the lock is open, or if the lock is in the ALARM state.
- `display` - a module to transform given inputs like the current state of the lock, and the current sequence of buttons into the correct outputs for the seven-segment displays, RGB LED, and the "right" bus of red LEDs.

A helpful way to think of this lab is to think of it as a giant Moore model state machine (why Moore?).  The next state and current state are contained within your `fsm` module, with the inputs determining what the next state should be, and the output logic is in the `display` module, which will determine what to display on the seven-segment displays and RGB LED based on the current state of the lock.

### 2.1: Generate states for our state machine

To summarize, you will need the following states for your lock:

- **INIT** - The lock is waiting for the user to press the **W** button to confirm the key sequence, or to relock the lock once opened.  We start in this state, in which the user is expected to press any of 0-F to create an 8-key sequence until W is pressed to confirm it.  Once W is pressed, we go to **LS0**.
- **LS0 - LS7** - The lock is waiting for the user to input the next key in the sequence.  **LS0** indicates that the user must now press the first button in the sequence, **LS1** indicates that the user must now press the second button, and so on.  If the state machine is at **LS7**, and the user presses the correct button, the lock should transition to **OPEN**.  If the user presses the wrong button at any state from **LS0** to **LS7**, the lock should transition to **ALARM**.
- **OPEN** - The lock has been opened, and is waiting for the user to press the **W** button to relock the lock.
- **ALARM** - The lock has been opened, but the user has entered an incorrect sequence.  The lock will sound an alarm until the user presses the **3-0-W** button combo to reset the lock.

To define states in SystemVerilog, we will make use of a feature borrowed from C called **enums**.  Enums, short for enumerations, specify states as a list of named constants.  For example, we can define the states of our lock as follows:

```verilog
typedef enum logic [3:0] {
  LS0=0, LS1=1, LS2=2, LS3=3, LS4=4, LS5=5, LS6=6, LS7=7,
  INIT=8, OPEN=9, ALARM=10
} state_t;

```

Go ahead and put this block of code **above** your top module.  Defining this outside of any modules puts it in a **global** scope, making the state names accessible to all modules.

With FSMs, it is common to use a `typedef` to define a new type for each of the states that our state machine will traverse, and then use an `enum` to define the states.

Breaking down this definition - we are defining a new type called `state_t` that is a 4-bit vector.  This allows for us to write multiple modules that depend on these states, without hardcoding the values for each state into each Verilog module in case we need to change them later.

The `logic [3:0]` keyword specifies that our `state_t` data type is 4 bits wide, to account for larger numbers like 8, 9 and 10, which we used above.  The list of states is then specified inside the curly braces `{}`.  While it is not necessary to assign values in order, we do this so you know what the actual values are when you simulate it on the FPGA.

### 2.2: Determine next state logic for each state

Now that we have our states, we need to determine how the state machine will transition from one state to another.  This is done by specifying the next state logic for each state.

For example, if we are in state **LS0**, and the user presses the correct button from 0-F, we should transition to state **LS1**.  If the user presses the wrong button, we should transition to state **ALARM**.  If the user presses the **W** button, we should transition to state **LS0** if we were in states **LS0 - LS7** or **OPEN**.  If a button press occurs that we didn't account for, our lock must remain in the same state.

We start by defining a "state variable" that will hold the __current state__ for the lock.  We'll call it `lockstate`.  We'll also create a `n_lockstate` variable to hold the __next state__, which we'll use later on.

**Under our `fsm` module**, We can define it as follows:

```verilog
state_t lockstate, n_lockstate;
```

Keep in mind that even though we call it a "variable", the underlying hardware for our `state_t` types is a __register__ of 4 bits, or 4 flip-flops.  We then write Verilog code to update the `lockstate` to `n_lockstate` on the next rising edge of the clock, based on the current state and the user input - as we would do with any register.  __This is the essence of a state machine__.

Connect `lockstate` to `state`, our output.  (Remember that outputs go on the left hand side of an assignment.)  Therefore, as we update `lockstate` to `n_lockstate` on the next rising edge of the clock, `state` will immediately mirror `lockstate`, allowing the other modules to know what state the lock is in.

We know that we will only change states on user input.  Therefore, we need to create a way to update our current state (`lockstate`) to our next state (`n_lockstate`) whenever a button is pressed.

Implementing a state machine in Verilog requires that we split the __current__ and __next__ states into two blocks, `always_ff` and `always_comb` respectively.  On every rising clock edge, the current state of the lock, implemented in the `always_ff`, will be updated to the next state, implemented in the `always_comb`.

Here is how your current state should be implemented:

```verilog
always_ff @(/* on the rising edge of clk or rising edge of reset */) begin
    if (reset) begin
        // initialize lockstate to INIT
    end else begin
        // update lockstate to n_lockstate
    end
end

```

`reset` goes high when you press 3-0-W on the FPGA to assert the top-level reset.  If this occurs, `lockstate` should be set to `INIT`.  Otherwise, `lockstate` should be set to `n_lockstate` on the next rising edge of the clock.  Notice that we don't need to say `else if (clk)` because it is already implied if `reset` is not high.  <u>You should never have to say `else if (clk)`.</u>

Before we implement the logic for our next state `n_lockstate`, we'll first create two `logic` signals to hold helpful information, so that it's easier to check conditions in the next state block.  These 1-bit signals should be called `M` and `R`.  This is how we can abstract things so that we don't have to write out the same condition multiple times in the next state block.

`M`, for Match, should be set to 1 if the user pressed a button that matched the current button in the sequence.  Create an assignment that sets `M` to 1 if the button just pressed (which comes from `keyout`) is the same as the current button in the sequence (which is `seq[~lockstate]`), and 0 otherwise.

`R`, for Relock, indicates if W (which is also our relock button) was pressed.  Create an assignment that sets `R` to 1 if the button just pressed was W (which comes from `keyout`), and 0 otherwise.

Below our `always_ff` block, we can now create the next state logic as follows:

```verilog
always_comb begin
    casez({lockstate, M, R})
        // fill in the next states here...
    endcase
end

```

Notice the use of the concatenation operator (`{...}`).  This allows us to combine the signals so we can check all of them in a single condition, instead of three.  Keep this in mind for future steps.

We'll now fill in the `casez` statement by giving you an example.  We'll start with the **INIT** state.  Recall that in this state, we are waiting for the user to press any of 0-F to create an 8-key sequence until W is pressed to confirm it.  Once W is pressed, we go to **LS0**.

We can implement this as follows:

```verilog
casez({lockstate, M, R})
    {INIT, 1'b?, 1'b1}: n_lockstate = LS0;
    // fill in the rest of the states here...
endcase

```

The `?` is a wildcard character (also a **don't care** - remember this?) that matches `M` regardless of whether it is 1 or 0, which is why we use `casez` instead of `case`.  This saves us from having to write out both cases as separate conditions.  We can use this to our advantage to simplify our next state logic.

For the rest of the conditions, we can set up a **finite state machine diagram**, or **FSM diagram**.  You will need to translate this state diagram into corresponding next state statements in the `casez` structure. ### 3.1: Set up the seven-segment displays and RGB LED

In the `display` module, we'll be using the seven-segment displays to display one of three messages:

- The word "SeCuRE" (when in LS0-LS7), with the decimal point of each seven-segment display (ssX[7]) indicating which bit of the sequence has **yet** to be pressed.
- The word "OPEN" (when in the OPEN state).  This indicates the lock is open.  In this state, you should be able to go back to SeCuRE by pressing W.
- The phrase "CALL 911" (when in the ALARM state).  In this state, the red LED should flash at a rate of 2 Hz, and the lock should remain in this state until the **3-0-W** button combo is pressed to reset the lock.

Note that `ssdec` cannot be made to show `SeCuRE`, `OPEN`, or `CALL 911`, which have custom letters like P and R.  Therefore we'll need to add logic to connect the seven segment displays either to the ssdec instances, or directly to values, depending on the current state.

So that you don't waste time and/or make mistakes coming up with the bit patterns to display these phrases on the seven-segment displays, we'll give them to you here:

```verilog
// "SeCuRE" - 64'b01101101_01111001_00111001_00111110_01010000_01111001;
// "OPEN" - 64'b00111111_01110011_01111001_01010100;
// "CALL 911" - 64'b00111001_01110111_00111000_00111000_00000000_01100111_00000110_00000110;

```

If we connect any one of these bit patterns to the seven-segment displays, it displays that particular string - give it a try with a simple `assign` statement in the `top` module, and make sure to comment it out before you start working on the display.  You can use the `localparam` keyword to assign these to keywords that you can then assign to the displays.  The syntax is `localparam name = YY'b...`.

Using the states you built above, connect the displays so that they exhibit the following behavior.  Do this in a new `always_comb` block in the `display` module, with a `case` statement for each of the states.  (This is similar to a C `switch` statement.)

```verilog
always_comb begin
    case(state)
        statename1: begin
            // what happens when state == statename1?
        end
        statename2, statename3, statename4: begin
            // you can also combine multiple states
        end
        default: begin
            // what happens when state is none of the above?
            // best to have this to catch any errors - set all outputs to zero.
        end
    endcase
end

```

- If you're in INIT, the displays and RGB LED must be blank.
- If you are in the LS0-LS7 states, you should show "SeCURE" but connect the decimal points (ssX[7]) such that when you're in LS0, ss7[7] is on, or in LS4, ss3[7] is on, etc.  The other decimal points should be off.  Turn on the `blue` LED when in this state and turn off `green` and `red`.

   - You should not have to create a block for each of the LSx states.  You can combine them into one block as shown above.
   - The "SeCuRE" message is shown in the table above, with 1-bit zeroes where the decimal points are.  How do you make use of this to light up the correct decimal point for each state?  (Hint: you need to OR the message with a 1 at the right position, depending on the state.)
      - Start by determining where the decimal points are with respect to the `ss` bus.
      - Create a formula based on your current state that will give you the correct amount to shift the 1 by, in order to OR it with the `ss` bus to light up the correct decimal point.
      - You may find you need to multiply by a number that is a power of 2.  Multiplication and division by powers of 2 can be done with the `<<` and `>>` operators, respectively. (eg. multiplying by 2 is the same as shifting left by 1 bit.)

- If you're in the OPEN state, show the OPEN message, and the `green` LED must be turned on while red and blue are off.
- If you're in the ALARM state, show the "CALL 911" message, and use the clock prescaler module you wrote in the lab assignment to flash `red` on and off at a rate of 2 Hz, while the other LEDs are off.
